# Security Policy

## Supported Versions

| Version | Supported          |
| ------- | ------------------ |
| 3.x     | :white_check_mark: |

## Reporting a Vulnerability

If you discover a security vulnerability in Mass Migrator, please report it responsibly.

**Do NOT** open a public GitHub issue for security vulnerabilities.

Instead, please report vulnerabilities by:

1. Emailing security concerns to the project maintainers
2. Using GitHub's private vulnerability reporting feature (https://github.com/massmigrator/mass-migrator/security/advisories/new)

## Security Controls

This project implements multiple security layers:

- **SQL Injection Prevention**: Multi-layer identifier validation, parameterized queries
- **JavaScript Sandbox**: Comprehensive goja VM hardening with prototype chain freezing
- **Path Traversal Prevention**: Symlink resolution and prefix containment checks
- **Credential Redaction**: SecretString type with automatic redaction in logs
- **TLS Enforcement**: Minimum TLS 1.2 required for Kafka and S3 connections

## Known Limitations

The comprehensive review on 2026-05-31 identified three Critical Phase 2A
findings affecting daemon control, run-lock semantics, and test scaffolding in
the production binary. All three have been remediated in subsequent hardening
waves; the section below records the gaps and the fixes for operator
visibility.

### Recent hardening

#### Daemon control socket authentication (was 2A-Critical-1)

The control socket previously accepted any local connection. The socket is now
created with `0o600` permissions and every connection is gated by
`authorizePeer`, which verifies peer credentials via `SO_PEERCRED` on Linux
and `getpeereid(2)` on Darwin. Connections from a UID other than the daemon's
own are rejected with `ERR unauthorized`. On platforms without peer-credential
support the socket file mode remains the sole boundary, so operators should
deploy on Linux or Darwin for the full protection.

#### Run-lock semantics on Oracle and SQLite (was 2A-Critical-2)

`AcquireRunLock` previously returned `nil` on Oracle and SQLite, silently
permitting two replicas to "acquire" the same run. Both backends now insert a
sentinel row into a `run_locks` table inside the same transaction; the unique
constraint on `run_id` causes the second acquirer to receive
`ErrLockNotAcquired`. Operators no longer need external coordination when
running the daemon against an Oracle or SQLite state store.

#### Test scaffolding in production binary (was 2A-Critical-3)

`internal/pipeline` test helpers (`MockStateWriter`, `TestDataGenerator`,
`TestExecutionContextBuilder`) and the `testing` package import in
`internal/license/gate.go` have been removed from the non-test compilation
unit. `go list -deps ./cmd/mass-migrator` no longer includes `testing`, and
operators can run the same verification themselves to confirm the binary they
ship does not carry the test runtime.

#### License clock validation hardening (was 2A-H4)

Paid tiers (`pro`, `enterprise`) now require at least two independent clock
sources for expiry validation; the single-clock path is fail-closed with
`ErrInsufficientClocks`. A persisted high-water mark
(`~/.mass-migrator/clock_high_water`, mode `0o600`, atomic rename) records the
highest-ever-observed clock value and rejects system clocks rolled back beyond
the grace period (`ErrClockRollback`). Free / evaluation / dev tiers accept a
single clock as before. The minimum can be tuned via the `SetMinClocks` helper
for audited air-gapped deployments. Defeats the `date -s "$past"` plus
NTP-unreachable bypass described in the prior review.

#### NTP server hardening (was 2A-H5)

The license validator no longer trusts a user-supplied `MM_NTP_SERVER` value.
Three well-known public NTP servers (`time.cloudflare.com`, `pool.ntp.org`,
`time.google.com`) are hardcoded as defaults. To use a custom server, operators
must set BOTH `MM_NTP_SERVER_OVERRIDE=host:port` AND
`MM_ALLOW_NTP_OVERRIDE=true`, analogous to the `MM_ALLOW_INSECURE_TLS` pattern.
The legacy `MM_NTP_SERVER` variable is ignored with a one-time warning.
Responses are queried in parallel and must reach quorum (≥2 servers responding
within a 5-minute spread); the median is returned. The implausibility filter
is tightened to `year ∈ [2024, currentYear+5]` to limit attacker latitude.

## Verifying releases

Releases are signed using Sigstore (Cosign keyless mode) and ship with SLSA L3
provenance generated by the GitHub Actions release workflow. Container images
are published to GitHub Container Registry (GHCR) with native OIDC attestations.

### Container image signature (recommended)

Pull and verify signatures from GitHub Container Registry (GHCR):

```bash
# Verify image signature
cosign verify \
  --certificate-identity-regexp '^https://github\.com/massmigrator/mass-migrator/\.github/workflows/release\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/massmigrator/mass-migrator:v<VERSION>

# Or pull verified image with cosign
cosign pull --print-attestations ghcr.io/massmigrator/mass-migrator:v<VERSION>
```

Docker Hub images (`massmigrator/mass-migrator`) are mirrors of GHCR and carry
equivalent signatures. Verify GHCR as the source of truth.

### Binary signature

```bash
cosign verify-blob \
  --certificate mass-migrator_<ver>_linux_amd64.tar.gz.pem \
  --signature mass-migrator_<ver>_linux_amd64.tar.gz.sig \
  --certificate-identity-regexp '^https://github\.com/massmigrator/mass-migrator/\.github/workflows/release\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  mass-migrator_<ver>_linux_amd64.tar.gz
```

### SLSA provenance

```bash
slsa-verifier verify-artifact mass-migrator_<ver>_linux_amd64.tar.gz \
  --provenance-path mass-migrator_<ver>_linux_amd64.tar.gz.intoto.jsonl \
  --source-uri github.com/massmigrator/mass-migrator
```

Dependencies are monitored via Dependabot. The project uses only well-maintained, actively updated packages.
